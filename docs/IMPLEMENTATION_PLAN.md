# План прототипа и критерии выпуска

Статус документа — проект. Таблицы ниже задают проверки для физического стенда. На дату исследования исполнение и совместимость не измерялись. Архитектура и контракт описаны в [ARCHITECTURE.md](ARCHITECTURE.md) и [PROTOCOL.md](PROTOCOL.md).

## Текущее состояние

Этап 1 выполнен для Windows-части: хост читает CPU и RAM, поднимает TLS-сервер, сопрягает телефон по приглашению и отдаёт поток `hello` → `catalog` → `snapshot`. Проверки выполнены тестами и запуском на этой машине, Android-клиент не начат.

| Проверка этапа 1 | Состояние |
| --- | --- |
| Сбор CPU и RAM через Win32 | Готово. Значения меняются под нагрузкой, ноль отличается от ожидания замера. |
| Установка и запуск `.exe` | Готово для сборки из исходников. Установщик, автозапуск и правило firewall относятся к этапу 5. |
| TLS, отпечаток и отказ до отправки секретов | Готово: `401` без токена, `400` при чужом `Host`, `403` при `Origin`. |
| Сопряжение по приглашению и отзыв доступа | Готово: одно приглашение, отдельный токен на телефон, отзыв закрывает сокет. |
| Каталог и снимок | Готово: ревизия каталога, `seq` в пределах epoch, `ageMs` только для `ok`. |
| Медленный клиент | Готово: буфер одного снимка, тайм-аут отправки закрывает только этот сокет. |
| Один физический телефон в LAN | Не проверено: Android-клиента нет, устройства к машине не подключено. |

Что осталось до конца этапа 1: Android-клиент, проверка на физическом телефоне, экран панели с карточками, восстановление потока после смены сети. GPU и VRAM, PDH для дисков, LHM, история и пресеты остаются этапами 2–4.

## Этапы

| Этап | Работа | Что должно быть показано |
| --- | --- | --- |
| 1. Сквозной прототип | Сбор CPU и RAM через Win32, минимальные UI Windows и Android, Kestrel/OkHttp, TLS, сопряжение и каталог со снимком. | Один физический ПК и один физический телефон. Реальный замер меняется под нагрузкой. Доступ без токена и подмена сертификата отклоняются. |
| 2. Базовые метрики | PDH для дисков и эксперимента с WDDM, DXGI для GPU-инвентаря, тесты iGPU+dGPU и VRAM. | Выбранный для каждого GPU источник даёт верные атрибуцию и семантику, а пропуски видны на панели. |
| 3. Расширенные датчики | Проверить LHM, выборочные API драйверов и PawnIO. Добавлять только подтверждённые датчики и нужный IPC. | Сравнение на стенде с датчиками HWiNFO или вендорной утилитой. Проверка прав и чтения без воздействия на управление вентиляторами. |
| 4. Панель и история | Карточки, пресеты, Room, настройки, пустые состояния, диагностика. | Поворот без второго сокета, сохранение между запусками, правдивые значения и разрывы, сохранение последнего времени замера. |
| 5. Подготовка сборок | Установщик Windows с правилом LAN, APK, лицензии, долговременные прогоны и журнал матрицы. | Проверка установки, запуска, обновления, удаления, отзывов доступа, совместимости драйверов и ресурсных лимитов. |

Режим симуляции отдаёт заранее заданный сценарий каталога и снимков через тот же контракт. Он покрывает состояния UI, разрывы, скачки ревизии, медленного клиента и нагрузку БД. Режим явно помечается на экране и не учитывается как испытание физических датчиков.

## Матрица совместимости

| Конфигурация | Что проверять | Приоритет |
| --- | --- | --- |
| Windows 11 x64, обычные права, NVMe, AMD Ryzen + Radeon или первый доступный ПК | Win32, PDH, DXGI, память, распределение показаний по GPU, базовое сопряжение, firewall Private. Записать точные модели. | Первый стенд |
| Windows 11 x64, Intel CPU/iGPU и гибридный ноутбук Intel + NVIDIA | Движки 3D/compute/decode, UMA и dedicated VRAM, сон/возврат, два адаптера. | До заявлений о поддержке таких конфигураций |
| Windows 11 x64, NVIDIA dGPU или Intel Arc | Сопоставить PDH и показания vendor API на доступных устройствах. | До заявлений о поддержке производителя |
| NVMe, SATA, USB-мост, RAID | Активность и скорости отдельно от температуры/SMART. Документировать каждый вариант контроллера. | NVMe первым, остальные по доступности |
| PawnIO установлен, отсутствует или источник требует повышения | HVCI/Secure Boot/Defender в штатной конфигурации, права, чтение датчиков, работа базового Host при отказе. | До включения расширенных датчиков в поставку |
| Два физических Android на разных версиях ОС | Камера, разрешения, крупный шрифт, смена сети, уход в фон, ресурсы. На Android 17 с target ≥37 — разрешение LAN и отказ. | Один на этапе 1, два перед выпуском |
| Windows 10, ARM64, Windows Server, Android-версии вне тестовой матрицы | Отдельное решение о поддержке, отдельная установка и проверка. | Будущее решение |

В журнале каждого прогона фиксировать номер сборки продукта, версию и билд ОС, BIOS, драйверы, провайдер, версии PawnIO и модулей, права, состояние защиты, сетевой профиль, модель телефона, target SDK, условия нагрузки и сырые измерения. Для каждой метрики ставить «подтверждена», «недоступна с причиной», «не проверена» или «ошибка». Результат относится к проверенному сочетанию оборудования и ПО.

## Функциональные проверки

- **Точность и семантика.** Прогоны idle, CPU-only, RAM allocation/release, 3D, compute, video decode, выделение VRAM при стабильной загрузке GPU и отдельное чтение/запись по дискам. Повторять нагрузку с тем же интервалом и сравнивать эквивалентные показатели с PerfMon, Task Manager, HWiNFO или вендорной утилитой. CPU time и utility, разные датчики температуры и разные метрики GPU записывать раздельно. Для EC/SMBus начинать с раздельных повторяемых прогонов, отдельно проверять совместный запуск.
- **Датчики и идентичность.** Проверить настоящий ноль, прогрев дифференциального счётчика, отсутствие прав, отключение провайдера, тайм-аут, появление/исчезновение устройства. Повторить после перезагрузки и с двумя GPU. Изменение каталога не должно привязать карточку к другому железу автоматически.
- **Транспорт.** Сопряжение обоими способами, истечение приглашения, параллельное погашение, потеря ответа и восстановление через session, чужой сертификат, просроченный leaf, неверный SAN, неверный токен, отзыв открытого соединения. Контролируемый TLS endpoint проверяет, что секреты не отправляются при отказе доверия. Отдельно проверить неподходящий Host/Origin, ограничения размеров и отсутствие секретов в диагностике.
- **Сеть и восстановление.** Wi‑Fi off/on, гостевая сеть с изоляцией, смена IP, профиль Public, конфликт порта, сон и рестарт Windows, уход Android в фон, поворот, ручное отключение. При быстром reconnect график сохраняет границу даже при соседнем `seq`, а дубликат стартового снимка не записывается дважды. Нагрузка от замедлившегося клиента не задерживает второй телефон.
- **Хранение и UI.** Проверить пресеты и выбор ПК после перезапуска, 24 канала в истории, лимиты и очистку базы, обновление состава каталога, масштаб, min/max, часовые изменения, недоступный датчик, отказ камеры, разрешений и Keystore. Протокол прогонов хранит ссылки на журналы и скриншоты только после их фактического получения.

## Начальные измеримые цели

Пороговые значения ниже являются предложением для пилота. После первого замера зафиксировать модель стенда и пересмотреть цели при наличии измеримой причины.

| Показатель | Как измерять | Стартовый порог |
| --- | --- | --- |
| Первый живой снимок | От подтверждения подключения сохранённого ПК до отображения первой валидной точки, 30 попыток в стабильной LAN. | p95 ≤3 с. |
| Частота и свежесть | Интервал между полученными снимками на монотонных часах Android, 10 минут при частоте источника 1 Гц и без искусственных обрывов. | p95 ≤1,5 с. При остановленном источнике UI показывает устаревание в пределах 6 с. |
| Доставка после замера | Временно синхронизировать часы стенда, записать разброс их смещения, сопоставить `seq` Windows и Android. При отсутствии такой синхронизации использовать интервалы и время первого снимка отдельно. | p95 ≤500 мс для передачи и отображения в стабильной LAN как цель после калибровки. |
| Восстановление | От восстановления достижимости уже сопряжённого ПК до следующего валидного снимка, 20 быстрых Wi‑Fi обрывов, отдельный тест долгого backoff. | p95 ≤10 с после системного сигнала о возврате сети. Без сигнала учесть текущий backoff. |
| Нагрузка ПК | 60 минут работы, обычный режим и отдельный прогон с повторяемой игровой/вычислительной нагрузкой. Суммировать Host и helper, CPU считать долей суммарной мощности машины. | Медиана CPU ≤1%, p95 ≤3%, суммарный working set ≤250 МиБ как ориентир. |
| История | 60 минут с 24 рядами при 1 Гц, UI со стандартными настройками. Замерить запрос и отрисовку, размер базы + WAL, число строк, ещё 60 минут для проверки плато. | p95 открытия истории ≤300 мс на первом тестовом телефоне, ≤100 000 точек и ≤50 МиБ DB+WAL. |
| Батарея телефона | Два 60-минутных прогона с одинаковыми яркостью, температурой, Wi‑Fi и режимом «Не гасить экран». Сравнить панель со статичным экраном приложения, записать доступный источник энергии и погрешность. | Дополнительный расход ≤3 процентных пунктов заряда за час на первом стенде как ориентир. |
| Изоляция медленного клиента | 10 минут стабильного клиента при искусственном зависании чтения у второго. Проверить период снимков, очередь и память. | Устойчивый клиент выполняет порог частоты, буфер каждого отправителя остаётся ограничен, неисправный сокет завершается по тайм-ауту. |

Для эквивалентных метрик критерии точности утверждаются после первого сопоставленного прогона и записи естественного разброса. Публикация поддержки требует совпадения смысла и единиц, объяснения расхождений и успешных сценариев из матрицы. См. [исследование](../reports/Мониторинг%20ПК%20с%20телефона.md).
