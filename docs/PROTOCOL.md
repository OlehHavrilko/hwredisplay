# Протокол HardwareDisplay v1

Проект спецификации. Маршруты и примеры предназначены для совместной реализации Windows и Android. Все ограничения ниже требуют проверки на целевой сборке и телефонах.

## Сопряжение и проверка ПК

Windows создаёт и сохраняет случайный `hostId` в формате UUID, ключ ECDSA P-256 и самоподписанный сертификат с DNS SAN `pc-<hostId>.hardwaredisplay.test`, EKU `serverAuth`, KeyUsage `digitalSignature` и конечным сроком действия. Закрытый ключ и конфигурация защищены ACL и DPAPI `CurrentUser`. Потеря ключа останавливает LAN-сервер с диагностикой. После явного сброса или смены сертификата телефон требует новое сопряжение. Это касается и планового обновления сертификата в v1.

QR содержит компактный UTF‑8 JSON. В ручном режиме пользователь переносит те же поля с экрана Windows, где отпечаток и код сгруппированы для удобства ввода. Android также принимает вставку всего доверенного JSON, который можно скопировать из Windows UI и перенести локальным способом. Демонстрационные значения ниже показывают только формат.

```json
{"v":1,"hostId":"1482a7c6-1d42-40af-869e-6e09ceab6de2","ip":"192.168.1.20","port":18443,"certSha256":"0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef","invite":"00112233445566778899aabbccddeeff"}
```

- `certSha256` содержит 64 шестнадцатеричных символа SHA‑256 от DER всего leaf. `invite` содержит 32 шестнадцатеричных символа 128 случайных бит. Начальный срок действия приглашения — 120 секунд для QR и 300 секунд для отдельно открытого ручного режима. Активно только одно приглашение, новое заменяет прежнее. Валидация также проверяет версию, UUID в канонической форме, числовой порт `1..65535` и RFC 1918 IPv4. Лимит ввода — 1024 байта. Разбор не принимает ссылки, произвольные пути и имена хостов.
- Для HTTPS и WSS Android строит URL с логическим DNS-именем ПК. Отдельный OkHttp client для сохранённого ПК возвращает только его числовой IPv4 из `Dns.lookup`, создавая `InetAddress` из байтов. HTTP Host, SNI и стандартная проверка SAN используют имя из URL. При изменении IP Android закрывает поток и заменяет клиент и пул соединений. Используются `Proxy.NO_PROXY`, выключенные redirects и SSL redirects, без системного DNS fallback. [OkHttp Dns](https://raw.githubusercontent.com/square/okhttp/parent-4.12.0/okhttp/src/main/kotlin/okhttp3/Dns.kt) · [OkHttp TLS](https://raw.githubusercontent.com/square/okhttp/parent-4.12.0/okhttp/src/main/kotlin/okhttp3/internal/connection/RealConnection.kt)
- Выделенный `X509TrustManager` принимает единственный ожидаемый самоподписанный leaf. Он сравнивает DER SHA-256 с перенесённым отпечатком, проверяет срок, профиль и самоподпись. OkHttp выполняет штатную проверку DNS SAN. Исключения, неправильное имя и любое несовпадение приводят к отказу до HTTP. `CertificatePinner` сам по себе проверяет SPKI после прохождения TLS-доверия. [OkHttp CertificatePinner](https://raw.githubusercontent.com/square/okhttp/parent-4.12.0/okhttp/src/main/kotlin/okhttp3/CertificatePinner.kt)
- Android генерирует 256-битный bearer, кодирует в base64url без padding, сохраняет как `pending` в зашифрованном состоянии и отправляет `Authorization: Bearer <token>`. Windows хранит SHA‑256 токена и исключает заголовок и тело запроса сопряжения из журналов. Android хранит шифротекст AES-GCM с новым IV на запись и ключом Android Keystore в `noBackupFilesDir`. [RFC 6750 §2.3](https://www.rfc-editor.org/rfc/rfc6750#section-2.3) · [Android Keystore](https://developer.android.com/privacy-and-security/keystore)

## Маршруты HTTPS

Сервер v1 слушает только TLS на выбранном LAN IPv4. Host должен совпадать с каноническим именем (с допустимым портом сервера). Для нативного API отклоняются запросы с `Origin`. Параметры аутентификации и данные сопряжения передаются после проверки TLS. Запросы и ответы сопряжения и сессии используют `Cache-Control: no-store` в ответах.

| Запрос | Успех | Ошибки |
| --- | --- | --- |
| `POST /v1/pair` с bearer и JSON | `201`, JSON с `v`, `hostId`, `clientId`. В одной транзакции погашается действующее приглашение и сохраняется клиент. | `400` формат, `403` недействительное приглашение, `409` конфликт с записью bearer, `413` тело больше 4 КиБ, `429` лимит запросов. |
| `GET /v1/session` с bearer | `200`, JSON с `v`, `hostId`, `clientId`. | `401` токен не принят. |
| `GET /v1/telemetry` с bearer, WebSocket Upgrade и `Sec-WebSocket-Protocol: hardwaredisplay.v1` | `101`, согласованный подпротокол `hardwaredisplay.v1`. | `400` неверный upgrade или версия, `401` токен не принят, `403` недопустимый Origin, `429` лимит сессий. |

```json
{"v":1,"invite":"00112233445566778899aabbccddeeff","clientName":"Телефон"}
```

```json
{"v":1,"hostId":"1482a7c6-1d42-40af-869e-6e09ceab6de2","clientId":"91b4b507-f37e-433a-ac06-b77b2a2f7990"}
```

Windows отвечает `201` после commit. Повторное погашение приглашения отклоняется, в том числе при одновременных запросах. Транзакция сопряжения ограничена 5 секундами, срок приглашения проверяется на этапе записи. Если ответ потерян, Android проверяет сохранённый `pending` bearer через `GET /v1/session` и активирует его только после успешного ответа с ожидаемым `hostId`. Первый `401` может прийти до commit. Клиент повторяет только `GET` в пределах 15-секундного окна, сохраняя pending при сетевой недоступности до следующей ручной проверки. После `401`, полученного по истечении окна, Android удаляет pending и предлагает создать новое приглашение. Отзыв на ПК атомарно исключает новые сессии и закрывает уже зарегистрированные сокеты с `1008`. Операция регистрации синхронизируется с отзывом. Android при `401` или `1008` для уже активной сессии останавливает автоподключение и показывает действие для повторного сопряжения.

## Кадры телеметрии

Один завершённый текстовый WebSocket message содержит один JSON-объект UTF‑8. Лимит собранного сообщения — 256 КиБ, предел каталога — 512 датчиков. Клиент прикладных сообщений в v1 не отправляет. Поддерживается один активный поток на телефон и до четырёх телефонов на ПК как начальная настройка. Сервер отправляет `hello`, полный `catalog` и затем полные `snapshot`. `hello` отправляется один раз на соединение и задаёт его единственный `streamEpoch`. Если epoch меняется, сервер закрывает существующий поток с `1001`, Android переподключается и получает новые `hello`, `catalog` и `snapshot`. WebSocket Ping/Pong служит для контроля живости транспорта. [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html)

```json
{"v":1,"type":"hello","hostId":"1482a7c6-1d42-40af-869e-6e09ceab6de2","streamEpoch":"d5fa3350-cbbd-4ccf-b989-94163a402745","samplePeriodMs":1000}
```

```json
{"v":1,"type":"catalog","revision":1,"devices":[{"deviceId":"cpu-01","kind":"cpu","label":"Процессор"}],"sensors":[{"sensorId":"cpu-01-time","deviceId":"cpu-01","metricKey":"cpu.time_busy.percent","label":"Занятость CPU по времени","unit":"percent","source":"win32.GetSystemTimes","samplePeriodMs":1000},{"sensorId":"cpu-01-package-temp","deviceId":"cpu-01","metricKey":"cpu.temperature.package","label":"CPU Package","unit":"celsius","source":"lhm.cpu.package","samplePeriodMs":1000}]}
```

```json
{"v":1,"type":"snapshot","streamEpoch":"d5fa3350-cbbd-4ccf-b989-94163a402745","revision":1,"seq":48,"capturedAtUtc":"2026-11-12T11:04:42.123Z","monotonicMs":48000,"samples":[{"sensorId":"cpu-01-time","status":"ok","value":0,"ageMs":4},{"sensorId":"cpu-01-package-temp","status":"unavailable","reason":"permission_denied","value":null}]}
```

- `streamEpoch` меняется при запуске сборщика и сбросе шкалы `seq`. `seq` растёт в пределах epoch на один за опубликованный Windows-замер независимо от числа слушателей. Положительные `seq`, `revision` и неотрицательное `monotonicMs` передаются целыми, ограниченными `2^53−1` для переносимости JSON. `monotonicMs` отсчитывается от запуска epoch и не убывает. `capturedAtUtc` — UTC времени публикации по часам ПК. Обязательный при `ok` `ageMs` равен разности `monotonicMs` снимка и времени последнего опроса на той же шкале. Он находится в пределах `0..monotonicMs`. Время относится к опросу сборщика.
- Полный `catalog` перечисляет ровно текущие дескрипторы и передаётся перед снимком каждой новой `revision`, даже если клиент пропустил предыдущие ревизии. Ревизия в рамках epoch растёт при изменении состава или метаданных каталога. Каждый снимок содержит ровно одну запись на датчик заявленной ревизии. Ожидаемые, но недоступные датчики могут иметь дескриптор со статусом `unavailable`. Датчик, о котором провайдер ничего не знает, может отсутствовать в каталоге. Оба случая оставляют пользовательскую карточку с диагностикой.
- Допустимые состояния замера: `ok` с конечным числом, `waiting` с `null`, `unavailable` с `null`, `error` с `null` и `stale` с `null`. Начальные коды причин включают `warmup`, `unsupported`, `not_applicable`, `permission_denied`, `provider_offline`, `read_failed`, `timed_out` и `expired`. `stale` означает, что провайдер не обновил значение к сроку; последнее полученное число клиент может показать отдельно с временем. Для редких источников `samplePeriodMs` определяет ожидаемый интервал. Повтор ранее полученной точки с тем же временем опроса не добавляется в график.
- `unit` задаёт канонические `percent`, `bytes`, `bytes_per_second`, `celsius`, `hertz`, `watt`, `volt`, `rpm` или `count`. Android преобразует единицы при отображении. `metricKey` описывает смысл и точку измерения, `sensorId` определяет экземпляр метрики на данном ПК. Изменение смысла или источника, влияющего на интерпретацию, требует нового ID и отдельной истории. `NaN` и бесконечность запрещены.

## Доставка, переподключение и история

Сборщик публикует неизменяемую пару каталог–снимок. У каждого сокета один отправитель и буфер одного нового снимка. При вытеснении промежуточных снимков отправитель берёт свежую пару, последовательно отправляет каталог при необходимости и снимок соответствующей ревизии. Переполнение пропускает устаревшую телеметрию, не останавливая сборщик. Тайм-аут отправки закрывает только медленный сокет. На подключении Android принимает актуальный снимок без replay. Неизвестный подпротокол, снимок без нужного каталога и превышение лимитов переводят поток в состояние ошибки. Закрытие `1002` используется для ошибки протокола, `1009` для превышения размера, `1011` для сбоя сервера.

Предлагаемые значения — connect timeout 5 с, ожидание `hello` 5 с, ожидание следующего валидного снимка 5 с при частоте 1 Гц, Ping каждые 15 с. Повторная попытка через 1, 2, 4, 8 и далее до 30 с с jitter. Настройки backoff сбрасываются после устойчивого поступления снимков. Ручное отключение, отсутствие LAN-разрешения, отказ авторизации или ошибка проверки сертификата останавливают повторы до действия пользователя. Потеря Wi‑Fi и возврат приложения на экран пересоздают попытку с актуальным маршрутом. Приложение показывает раздельно TCP-ошибку, ошибку идентичности, отсутствие доступа, несовместимую версию и отсутствие свежих замеров.

История дедуплицирует `(hostId, streamEpoch, seq, sensorId)`. При новом соединении помечается граница непрерывности уже при закрытии старого. Первый уникальный замер попадает в новый сегмент, даже если начальный снимок был дубликатом, а следующий `seq` соседний. Новый epoch, скачок `seq`, длительная пауза, смена часов и недоступность датчика также создают разрывы. UTC используется для подписей, `seq` и монотонное время — для порядка. Строки со статусом вне `ok` не включаются в min/max. Телефон хранит наблюдавшийся период без дозагрузки с ПК. См. [архитектуру хранения](ARCHITECTURE.md) и [критерии проверки](IMPLEMENTATION_PLAN.md).

## Реализовано в прототипе хоста

Раздел фиксирует решения, которые спецификация оставляла на этап реализации. Проверено тестами и запуском на этой машине; Android-клиент повторит эти же правила.

- `value` передаётся всегда, включая `null` у недоступного датчика. `reason` и `ageMs` пишутся только когда применимы.
- `hello` содержит `streamEpoch` строкой UUID и отправляется до `catalog`; при замене потока того же телефона старый сокет закрывается с `1001` и причиной `replaced`.
- `Host` обязан совпадать с `pc-<hostId>.hardwaredisplay.test` и портом сервера, иначе `400 bad_host`. Запрос с любым `Origin` отклоняется с `403`. Оба ответа содержат `Cache-Control: no-store`.
- Тело `/v1/pair` ограничено 4 КиБ на уровне Kestrel; превышение даёт `413` без разбора JSON.
- Одновременно активно одно приглашение с TTL 300 с; после успешного сопряжения оно гасится, а окно хоста создаёт следующее. Отдельный темп 120 с для QR появится вместе с экраном ручного ввода.
- Порт по умолчанию 18443; при занятости хост пробует 18444 и 18445 и показывает занятый порт в окне. Тело `ErrorResponse` содержит `v`, `error` и необязательный `reason`.
- Медленный сокет закрывается `1008` с причиной `slow_client` после тайм-аута отправки 5 с. Отзыв доступа закрывает активные сокеты `1008` с причиной `revoked`. `1002`, `1009` и `1011` остаются за ошибками протокола, размера и сервера.
- Провайдер, превысивший дедлайн 2 с, помечает свои датчики `stale` с причиной `timed_out`; повторный опрос не запускается, пока не завершится предыдущий вызов.
- `samplePeriodMs` равен периоду тика сборщика (1000 мс). Отдельные расписания групп появятся вместе с PDH и SMART.
- Каталог обнаруживается при старте и пересматривается раз в 10 с; ревизия растёт только при изменении состава или метаданных.
