# Как вывести датчики Windows на телефон

HardwareDisplay реализуем как локальное Windows-приложение и нативную панель Android. Существующие проекты уже демонстрируют опрос оборудования, трансляцию замеров в локальной сети, настройку карточек и историю. Основная техническая неопределённость — покрытие датчиков на конкретных платах, видеокартах и драйверах. Для собственного сборщика предлагается начать с Win32 и PDH, а дополнительные температуры и электрические показатели получать из LibreHardwareMonitorLib или API производителя после проверки. Сетевой контракт должен передавать каталог датчиков и актуальные снимки по WSS, а сопряжение — связывать телефон с проверенной идентичностью ПК. Исследование от 12 ноября 2026 года основано на документации и исходном коде. Испытания приложений, оборудования и предлагаемой архитектуры ещё не проводились.

## Референс уже реализует QR, WebSocket и базовый редактор

По названию Windows-окна, формату QR, порту `8765` и шести метрикам истории референс с высокой уверенностью определён как **Xeakaes/PcHWmonitor**. Точный установленный релиз неизвестен. В изученном коммите `764c5e33b8c79e333b00be8e444aa5a3e6872b31` Windows использует Python, FastAPI/Uvicorn, LibreHardwareMonitorLib или внешний LibreHardwareMonitor JSON, а для части системных показателей — `psutil`. Windows-версия собирается PyInstaller. Android-клиент использует Kotlin, Compose и Room. Сервер принимает `auth` с общим токеном и поддерживает опциональный WSS. Hub опрашивает источник один раз за тик и рассылает снимок, дожидаясь сетевых отправок с тайм-аутом. Android хранит час истории для фиксированных шести полей. README уже заявляет изменение порядка, ширины и видимости карточек, альбомную сетку и работу с несколькими ПК. Скриншот пустого графика сам по себе не устанавливает причину. Из сравнения следует конкретный набор улучшений, который можно проверять на одном ПК и телефоне. **Динамический каталог** допускает произвольную историю, сохраняет привязку при переименовании датчика и указывает причину отсутствия значения. **Отдельная учётная запись телефона** позволяет отозвать один клиент. **Независимая рассылка** ограничивает очередь каждого клиента и продолжает опрос при зависшей сети. ## Метрики Windows требуют нескольких источников

**Первый рабочий путь — CPU и RAM через штатные API Windows.** `GetSystemTimes` даёт накопленные времена, поэтому загрузка по времени рассчитывается из двух замеров с учётом idle внутри kernel. `GlobalMemoryStatusEx` даёт физическую память, доступный объём вычитается из общего. Для накопителей штатный PDH предоставляет показатели чтения, записи и времени активности по физическим дискам. Разные семантики надо оставлять видимыми. CPU time, utility диспетчера задач, commit и занятая физическая память описывают разные величины. [GetSystemTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getsystemtimes) · [MEMORYSTATUSEX](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/ns-sysinfoapi-memorystatusex) · [Счётчики дисков](https://learn.microsoft.com/en-us/windows-server/storage/storage-spaces/performance-history-for-drives)

**GPU и VRAM — отдельный эксперимент до обещания поддержки.** Кандидаты — PDH `GPU Engine` и `GPU Adapter Memory`, инвентарь и dedicated capacity из DXGI. Microsoft описывает общую загрузку диспетчера задач как загрузку самого занятого движка. Для PDH предстоит подтвердить формат экземпляров и группировку вклада PID по адаптеру и движку на целевых WDDM-драйверах. `IDXGIAdapter3::QueryVideoMemoryInfo` описывает бюджет и использование приложения, а суммирование показателей процессов может повторно учитывать разделяемые аллокации. Поэтому для VRAM нужен подтверждённый источник на уровне адаптера или API производителя с ясной семантикой. Занятые байты, процент заполнения и активность памяти должны иметь отдельные ключи. Для iGPU с UMA отдельные поля dedicated VRAM могут быть неприменимы. [Microsoft DirectX](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/) · [DXGI](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_4/ns-dxgi1_4-dxgi_query_video_memory_info) · [Проблемы process counters](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/gpu-process-memory-counters-report-wrong-value) · [NVML utilization](https://docs.nvidia.com/deploy/nvml-api/latest/api/structnvmlUtilization__t.html)

**LibreHardwareMonitorLib — первый кандидат для расширенных датчиков.** В изученном `0.9.6` библиотека сводит AMD ADL/PMLog, NVIDIA NVAPI/NVML, Intel IGCL и другие источники под общим интерфейсом. Температуры, напряжения, частоты и вентиляторы зависят от конкретного устройства, BIOS, драйвера и прав. Варианты при пробеле покрытия — AMD ADLX, NVIDIA NVML/NVAPI, Intel IGCL или самостоятельный Windows NVMe query для накопителей. Каждый источник должен сообщать доступность метрики и сохранять её смысл, например GPU core против Hotspot и CPU Package против Tctl/Tdie. [LHM v0.9.6](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/releases/tag/v0.9.6) · [ADLX Metrics](https://gpuopen.com/manuals/adlx/adlx-sdk-references/adlx-interfaces/performance-monitoring/iadlxgpumetrics/) · [NVML](https://docs.nvidia.com/deploy/nvml-api/nvml-api-reference.html) · [Intel IGCL](https://github.com/intel/drivers.gpu.control-library) · [Windows NVMe](https://learn.microsoft.com/en-us/windows/win32/fileio/working-with-nvme-devices)

**Драйвер и лицензии входят в проект поставки.** LHM перешёл с WinRing0 на PawnIO в `0.9.5`. Microsoft отмечает WinRing0 как уязвимый драйвер. Проверка PawnIO нужна на штатной конфигурации Windows с Secure Boot, HVCI и Defender. Если отдельной группе нужны права, чтение выполняет локальный helper, а интерфейс и сетевой сервер остаются под обычным пользователем. LHM включает ветки управления вентиляторами, поэтому проектный адаптер должен использовать чистые настройки и исключить вызовы управления. У MPL‑2.0, включённых модулей PawnIO, драйвера и установщика есть собственные условия. Перед распространением нужно проверить фактические бинарные зависимости, уведомления и права включения установщика. [Переход LHM](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/releases/tag/v0.9.5) · [WinRing0](https://support.microsoft.com/en-us/windows/security/threat-malware-protection/microsoft-defender-antivirus-alert-vulnerabledriver-winnt-winring0) · [Код управления AMD](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/blob/v0.9.6/LibreHardwareMonitorLib/Hardware/Gpu/AmdGpu.cs) · [LHM notices](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/blob/v0.9.6/THIRD-PARTY-NOTICES.txt) · [PawnIO](https://github.com/namazso/PawnIO/blob/2.2.0/README.md)

**HWiNFO подходит для сверки и как опциональный внешний источник.** Shared Memory в обычном HWiNFO64/ARM64 имеет 12-часовое ограничение. EULA требует явного разрешения на включение HWiNFO в комплект стороннего ПО и запрещает обход лимита. Отдельный SDK предоставляет API как интегрируемая DLL. Для продукта, который должен работать сразу после установки, базовый путь через собственный сборщик снимает зависимость от отдельного приложения. Для SHM и SDK нужно подтвердить условия использования в выбранном сценарии. [Таблица лицензий](https://www.hwinfo.com/licenses/) · [EULA](https://www.hwinfo.com/files/license.pdf) · [SDK](https://www.hwinfo.com/sdk/) · [Разбор источников Windows](../research_notes/Мониторинг%20ПК%20с%20телефона/windows-telemetry.md)

## Идентичность ПК и жизненный цикл потока влияют на историю

В предлагаемой реализации **Windows получает постоянное логическое TLS-имя, а IP остаётся адресом маршрута**. QR и ручной режим передают отпечаток сертификата и одноразовое приглашение с экрана ПК. OkHttp направляет TCP на числовой IPv4 через выделенный DNS-адаптер, сохраняя логическое имя в URL, SNI и проверке SAN. Специальный `TrustManager` принимает только ожидаемый leaf после сверки SHA‑256 DER, срока и профиля сертификата. Штатный `CertificatePinner` OkHttp проверяет SPKI после прохождения TLS-доверия, поэтому одного такого pin недостаточно для самоподписанного leaf. Практическую работу связки и отказ до отправки секрета нужно подтвердить на двух телефонах. [Kestrel endpoints](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/endpoints?view=aspnetcore-10.0) · [OkHttp TLS](https://raw.githubusercontent.com/square/okhttp/parent-4.12.0/okhttp/src/main/kotlin/okhttp3/internal/connection/RealConnection.kt) · [CertificatePinner](https://raw.githubusercontent.com/square/okhttp/parent-4.12.0/okhttp/src/main/kotlin/okhttp3/CertificatePinner.kt)

Сопряжение выполняется по HTTPS. Сервер атомарно погашает приглашение и сохраняет хеш отдельного bearer для телефона. Сам bearer защищается Android Keystore через шифрование в приватном хранилище. Сервер принимает WebSocket Upgrade после авторизации, а отзыв учётной записи закрывает её активные сокеты. Kestrel привязывается к выбранному IPv4. Правило Windows Firewall ограничивается Private и локальной подсетью. Android 17 при target SDK 37 и выше требует runtime-разрешение для прямого доступа к LAN, что входит в план испытаний целевого SDK. Гостевой Wi‑Fi, публичный профиль и отказ разрешения проверяются отдельно. [Android Keystore](https://developer.android.com/privacy-and-security/keystore) · [Android LAN permission](https://developer.android.com/privacy-and-security/local-network-permission) · [Windows Firewall](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/rules)

**Время измерения и непрерывность доставки хранятся отдельно.** ПК публикует полный каталог и снимки с номером ревизии, epoch и порядковым номером. Каждый отправитель держит только свежий снимок, а Android дедуплицирует повтор после подключения. Переподключение, пропущенная последовательность, смена epoch и отказ датчика отображаются разрывами графика. Room хранит ограниченный объём точек, а `metricKey` помогает перепривязать карточки при смене ПК. Эти решения позволяют отличить «нагрузка 0%», «источник недоступен» и «телефон показывает последнее известное значение». [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html) · [Room](https://developer.android.com/training/data-storage/room) · [Подробности LAN и Android](../research_notes/Мониторинг%20ПК%20с%20телефона/lan-android.md)

## Что решает первый физический стенд

Первый эксперимент должен дать два независимых результата: живой CPU/RAM на Android при проверенном сопряжении и таблицу доступных GPU/VRAM на Windows без повышения прав. Если WDDM-кандидаты не проходят сверку на нужном оборудовании, сетевой контракт уже готов принять вендорские источники с их собственной семантикой. Покрытие температур, PawnIO и возможность включения дополнительных бинарных компонентов определяют следующий объём релиза после этих проверок.
